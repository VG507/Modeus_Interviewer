# Modeus: план реализации MVP с фокусом на качестве интервью

Версия 1.0 · 16 ноября 2026 года

Отдельный план реализации по итогам критического разбора `Modeus_Interview_Dataflow.md` версии 0.4. Исходный документ не изменён: он остаётся контекстом будущей платформы. Для объёма первого MVP используем этот план. Ниже описана будущая работа, а не уже реализованные функции.

## 1. Цель и граница MVP

Проверить, может ли система раскрыть конкретный рабочий случай специалиста: выяснить действия, основания решений и проверку результата, а затем собрать полезную карточку без выдуманных дополнений.

Обязательный путь: выбранная тема → конкретный случай → адаптивные уточнения → итоговый черновик → просмотр и исправление → ручная проверка → карточка в публичном web-каталоге для хакатона.

Стартовые сценарии проверки относятся к Python backend. Первый — диагностика медленного SQL-запроса. Открытое интервью принимает роль из анкеты и определяет тему из рассказа, включая случаи из смежных IT-ролей. Качество за пределами проверенных сценариев оцениваем отдельно.

Главное доказательство результата — содержательное интервью и узнаваемое описание практики. Красивый чат, заполненные поля и число карточек сами по себе не являются успехом.

## 2. Объём первого выпуска

| Включаем | Как ограничиваем |
|---|---|
| Источники тем | Минимальный автоматический импорт вакансий с hh.ru для Python backend. Сохраняем URL, дату и текст. Ручная выборка остаётся запасным источником |
| Темы | В браузере интервью начинается с общего вопроса. Тему конкретного случая определяем по рассказу и сохраняем внутри сессии. Подготовленные темы остаются для целевых проверок через API |
| Контекст специалиста | Короткая анкета в начале сессии: роль, опыт, обязанности, существенные условия |
| Интервью | Текстовый web, один рабочий случай одновременно, один вопрос за ход. После разбора система переходит к следующей теме. Интервью завершает участник |
| Адаптация | Экстракция сведений, простой планировщик, формулировка вопроса |
| Управление | Пропустить, завершить, вернуться к сохранённой сессии |
| Карточка | Частичный черновик, исправление итогового текста, явные пробелы |
| Проверка | Простой экран редактора: принять, вернуть на доработку, оставить приватно |
| Каталог | Публичный список и страница опубликованной карточки; фильтр по теме при необходимости |
| Доступ | Готовый вход из кодовой основы, если пригоден; приватные материалы доступны владельцу и уполномоченному редактору |

Откладываем: Telegram, голос и STT, несколько профессиональных профилей, объединение аккаунтов, автоматическую подготовку новых профессий, embeddings, автоматическое слияние карточек, граф знаний, версии наборов знаний, LLM-кеширование, произвольную правку истории с каскадным пересчётом, отдельный экспортный сервис, виртуального эксперта и генератор учебных планов.

Публичный каталог сохраняем именно для хакатона. Это не обязательство делать его постоянной частью будущего продукта.

### Рыночный контекст для вопросов

1. Загружаем небольшую выборку вакансий для Python backend отдельной командой, до интервью. Проверяем пригодность клиента из проекта про компетенции. Повторный импорт обновляет вакансии по ID или каноническому URL и не создаёт дублей.
2. Из обязанностей и требований выделяем отдельно рабочие задачи, стек и условия работы. Сохраняем краткую сводку с датой, размером выборки и ссылками на источники. Задачи из выборки можно использовать для подготовки вопросов о рабочих эпизодах.
3. При формулировке уточнения передаём модели короткую выдержку из сводки, если её роль и задачи подходят к анкете и текущему случаю. Открытый первый вопрос и выбор темы из рассказа остаются основой интервью. Название технологии из вакансии может подсказать, о чём спросить, но в карточку попадают только сведения из ответов участника.
4. При сбое hh.ru используем последнюю сохранённую сводку. При её отсутствии или отсутствии подходящей роли интервью продолжается на анкете и ответах. Запросы к hh.ru не входят в цикл обработки ответа.

Эту работу ведём параллельно с редактурой и публикацией карточек. Перед показом проверяем импорт, повторный запуск без дублей и один сценарий с одинаковыми ответами, со сводкой и без неё. Критерий пользы — уточнение конкретной задачи или решения без приписывания эксперту рыночных требований.

## 3. Сначала определяем хорошее интервью

Подготовить небольшой проверочный набор до разработки полного интерфейса. Начальный ориентир — 6 коротких сценариев; это рабочие примеры, а не статистическая оценка качества.

| Сценарий | Ожидаемое поведение |
|---|---|
| «Обычно оптимизирую запросы» | Попросить конкретный случай, не начинать перечислять технологии |
| Подробный ответ сразу раскрывает несколько аспектов | Учесть все сведения и пропустить уже закрытые вопросы |
| «Добавил индекс» | Выяснить существенный пробел: основание выбора или способ проверки |
| Неудачный подход | Сохранить его как неудачу, не превратить в рекомендацию |
| Отказ или чужая зона ответственности | Прекратить ветку, предложить доступный человеку случай либо завершить |
| Неполный, неоднозначный ответ | Уточнить важную неоднозначность или сохранить пробел; не достраивать ответ |

Для каждого сценария человек заранее отмечает: известные факты, допустимые направления уточнения, недопустимые домыслы. Эталонной единственной формулировки вопроса не требуется.

Карточку и диалог оцениваем отдельно по четырём признакам:

| Признак | Признак успеха | Признак провала |
|---|---|---|
| Привязка к ответу | Вопрос использует конкретную деталь и раскрывает полезный пробел | Очередной пункт анкеты без связи с ответом |
| Новые сведения | Уточнение выявляет действие, условие, основание или проверку | Повторяет уже известное либо просит общие слова |
| Сохранение смысла | Итог сохраняет ограничения, отрицания и тип опыта | Ошибка стала советом, частный случай — универсальным правилом |
| Обоснованность | Существенные утверждения связаны с ответами | Модель добавила не рассказанные шаги или причины |

На разборе используем отметки «да / частично / нет» и короткое объяснение. Общий балл эксперту и искусственный процент качества не вводим.

## 4. Минимальное ядро интервью

### 4.1. Один цикл

1. Сервер сохраняет ответ до вызова модели.
2. Экстрактор обновляет сведения о текущем случае и выделяет существенные пробелы.
3. Код проверяет структуру и ссылки, обновляет состояние.
4. Планировщик выбирает цель уточнения или переходит к следующему случаю.
5. Интервьюер формулирует один вопрос по выбранной цели.
6. Сервер сохраняет вопрос, web показывает его пользователю.

Экстрактор, состояние и планировщик разрабатываются как один тесно связанный участок. Сначала проверяем один полный ход, затем подключаем интерфейс. Все компоненты могут жить в одном backend; отдельные микросервисы не нужны.

### 4.2. Что извлекаем

Минимальные поля: задача и контекст, действия, решения и их основания, проверка результата. Дополнительно — ошибки и ограничения, если они появились в рассказе.

Каждое существенное утверждение содержит ссылки на сообщения-основания. Неизвестное остаётся неизвестным. Вакансия объясняет выбор темы, но не доказывает опыт человека. Сведения модели о профессии не записываются как слова специалиста.

Сохраняем краткий список пробелов и уже заданных намерений. Отдельный сложный реестр покрытия всех аспектов профессии не строим.

### 4.3. Правила выбора следующего вопроса

Приоритеты сверху вниз:

1. Явная команда завершить или пропустить.
2. Существенная неоднозначность, без которой можно исказить рассказ.
3. Получение конкретного случая, если пока есть только общее описание.
4. Недостающие действия и последовательность.
5. Основание важного решения: почему выбран этот способ и при каких условиях.
6. Способ проверки результата.
7. Дополнительный вопрос об ошибке или ограничении, если он полезен для этого случая.
8. Переход к следующей теме или другому случаю.

Не задаём вопрос только потому, что поле пустое. Не просим раскрывать посторонний аспект. Если ответ закрыл несколько полей, учитываем их все. После двух безрезультатных уточнений предлагаем другой случай.

### 4.4. Когда заканчиваем

Рабочий случай достаточно раскрыт, когда понятны задача и существенные условия, основные действия, основание хотя бы одного важного решения и проверка результата. Если значимого выбора в случае нет, это фиксируется явно, а не выдумывается ради схемы.

После разбора просим рассказать другой рабочий случай и определяем тему по новому ответу. В целевом интервью с заданной темой API предлагает следующую тему из каталога. Ошибки, частота и дополнительные варианты не обязательны. Участник может закончить в любой момент, в том числе посреди случая.

Для пилота используем мягкий ориентир 10–15 минут. Синтез карточки запускается по команде участника завершить интервью.

### 4.5. Вызовы модели

Одна текстовая модель, разные инструкции: экстрактор, интервьюер, синтезатор. По умолчанию два последовательных вызова на ответ; при завершении новый вопрос не генерируется. Если задержка мешает беседе, сначала измеряем длительность каждого этапа и сокращаем контекст. Объединение вызовов рассматриваем только после проверки, что это не ухудшает качество и управляемость.

## 5. Минимальные данные и поведение при ошибках

| Сущность | Что хранит |
|---|---|
| User | Идентификатор, данные готового механизма входа, право редактора |
| Topic / Source | Тема и сохранённые основания её выбора; связь без полноценной рыночной аналитики |
| InterviewSession | Владелец, контекст на начало сессии, тема, статус, происхождение, версия состояния, краткая структура случая |
| Message | Вопрос или ответ, порядок, время, ключ повторной отправки; для обработанного ответа — результат извлечения |
| KnowledgeCard | Структурированный черновик, текст, ссылки на сообщения, автор, происхождение, публикация, результат проверки |

Структуры извлечения и состояния на старте можно хранить в JSON-полях. Отдельные таблицы вводим при появлении потребности, а не по числу терминов в архитектуре. Используем имеющуюся БД пригодной кодовой основы; если основы нет — одну реляционную БД без дополнительной поисковой инфраструктуры.

Обязательные гарантии: проверка владельца, сохранение ответа до обработки, один активный ход на сессию, защита от повторной отправки, отклонение устаревшего результата. При сбое модели ответ остаётся, пользователь видит ошибку и возможность повтора. Долгий запрос показывает состояние обработки; полноценная система SSE с воспроизведением событий не обязательна.

Редактирование: последний ответ можно исправить до продолжения обработки. После начала обработки история в MVP не редактируется; уточнение передаётся новым сообщением. После завершения пользователь исправляет итоговый черновик. Пересчёт всей истории не реализуем.

Сохраняем технические сведения вызова: версия инструкции и схемы, фактическая модель, длительность, результат или ошибка. Этого достаточно для разбора проблем пилота.

## 6. Карточка и публикация

Карточка содержит: название задачи, контекст, основные действия, решения и основания, проверку результата, ограничения и неизвестное. Пустые дополнительные разделы не показываем. Существенные утверждения имеют внутренние связи с ответами; чужой диалог публично не открывается.

Поток: приватный черновик → просмотр и исправление владельцем → согласие на публикацию → ручная проверка → каталог. Редактор может вернуть материал с коротким замечанием. Неполный материал можно сохранить приватно без принуждения к публикации.

Публикация и проверка — разные признаки. Минимум: публикация `draft / in_review / published`, проверка `unreviewed / reviewed / needs_changes`. Для MVP не строим сложный workflow. Обновление уже опубликованной карточки через новые вклады откладываем; при обнаруженной проблеме редактор может снять её с публикации.

Происхождение `human / synthetic` сохраняется неизменяемо, отдельно от проверки. Примеры из внешнего ChatGPT могут использоваться для показа механизма и каталога, но не считаются подтверждением реальной практики. В презентации объясняем происхождение примеров; обязательные продуктовые плашки и отдельный режим демонстрации не добавляем. При дальнейшей выборке данных происхождение должно учитываться явно.

Дубликаты в первом выпуске проверяет редактор: оставить отдельную карточку или вернуть на доработку. Автоматическое слияние, независимые подтверждения и типы отношений между знаниями не реализуем.

## 7. Порядок реализации и условия перехода

### Этап 0. Проверить кодовую основу и зафиксировать объём

Кандидат — `https://github.com/kr1p043k/compare_competencies`; ранее обсуждавшийся commit — `9990d8b2e188722e89ef700889a14b89e25d8955`. Его пригодность этим планом не подтверждается.

Проверить инструкции, лицензию, запуск, зависимости и только нужные части: LLM-клиент, web-оболочку, БД, вход и импорт вакансий. По каждому компоненту записать «берём / адаптируем / заменяем / откладываем» и основание. Не переносить весь проект, аналитику, ML-модули и учебные программы автоматически.

Ограничить первичную проверку одним рабочим блоком команды, ориентир — до половины дня. Если запуск или адаптация выходят за этот предел, отдельно оценить конкретный блокер и выбрать минимальную замену. Не тратить весь срок хакатона на ремонт оболочки.

Результат: выбранный стек, подтверждённые компоненты, одна профессия, первая тема и владелец каждого участка. Доступ к LLM проверен реальным запросом. Полноценный парсинг не блокирует интервью: допустим сохранённый набор вакансий.

### Этап 1. Проверить интервью без полного web

Подготовить сценарии из раздела 3 и инструкции трёх LLM-ролей. Собрать минимальный запускаемый цикл: ответ → извлечение → правило → уточнение → итог. Проверить его на сохранённых примерах, включая подробный ответ и отказ.

Результат: система задаёт содержательное уточнение, пропускает уже раскрытое и не добавляет несуществующие факты. Явные ошибки исправлены до расширения интерфейса.

### Этап 2. Провести первый ручной пилот с человеком

Провести одно короткое интервью с представителем выбранной профессии. Участника приглашает команда; при отсутствии специалиста разрешена техническая репетиция, но проверка качества остаётся незавершённой. Интерфейс может быть минимальным; важно сохранить вопросы, ответы и карточку.

После разговора спросить: где вопрос был лишним, какую важную деталь пропустили, узнаётся ли собственная практика в карточке. Исправить правила и инструкции по конкретным ошибкам. Не расширять банк и схему, пока не проверены простые исправления.

Результат: хотя бы один понятный рабочий случай с основаниями решения и проверкой результата; нет существенных домыслов. Если этого нет, повторяем этот этап, а не компенсируем интерфейсом.

### Этап 3. Собрать устойчивый текстовый web

Подключить вход, анкету и экран открытого интервью. Из конкретного ответа определить тему, затем уточнять один случай за раз. После разбора попросить рассказать другой эпизод. Добавить состояние обработки, пропуск, повтор при сбое, возврат к сохранённому разговору и завершение по команде участника.

Результат: новый пользователь проходит разговор без помощи разработчика. Обновление страницы и повторная отправка не теряют ответ и не создают лишний ход. Автоматическая проверка фильтрует реплики для фактов карточки. После завершения открывается приватный черновик.

### Этап 4. Довести карточку до каталога

Добавить синтез по сохранённому материалу, исправление черновика, согласие, экран редактора, публичный список и подробную карточку. Источники темы и происхождение сохраняются внутри данных.

Результат: из нового интервью получается проверенная опубликованная карточка. Приватные материалы не становятся доступны через каталог.

### Этап 5. Проверить качество и подготовить показ

Начальный ориентир — 3 коротких интервью с людьми выбранной профессии, включая ранний пилот. Это выявление проблем, а не доказательство достоверности всей базы. Карточку просматривает рассказавший случай специалист; хотя бы одну — другой специалист на понятность условий и логики действий.

Проверить сценарии из раздела 3 и технические случаи из раздела 8. Устранить критические ошибки. Записать оставшиеся ограничения и подготовить сохранённый пример для показа, если внешний API недоступен. Сохранённый пример представляется как заранее подготовленный, а не как живой запрос.

Результат: команда может показать, какая деталь ответа изменила следующий вопрос и что полезного это добавило в карточку.

## 8. Проверки готовности

| Проверка | Что должно произойти |
|---|---|
| Ответ содержит действия и проверку | Вопрос о проверке повторно не задаётся |
| Ответ слишком общий | Система запрашивает конкретный случай |
| Есть значимый выбор без объяснения | Уточняется основание выбора, если человек может его раскрыть |
| Человек отказался | Ветка прекращается |
| Материала мало | Сохраняется частичный черновик с пробелами |
| Описана ошибка | В карточке она остаётся ошибкой |
| Модель недоступна или вернула неверную структуру | Ответ сохранён, доступен повтор, ложное знание не записано |
| Двойная отправка, обновление страницы | Нет второго ответа или лишнего вопроса |
| Устаревший результат обработки | Не перезаписывает актуальное состояние |
| Другой пользователь открывает приватный материал | Доступ запрещён |
| Публикация | Нужны согласие владельца и решение редактора |
| Синтетический пример | Происхождение не меняется после принятия редактором |

Для планировщика и переходов состояния нужны небольшие автоматические проверки на сохранённых случаях. Для качества LLM — воспроизводимый прогон сценариев с человеческим разбором; сравнение с одной точной строкой вопроса не подходит. Проверки доступа и повторной отправки выполняем на уровне API.

К выпуску: все обязательные технические проверки пройдены; в просмотренных карточках нет существенных утверждений без основания в ответах или явной правке владельца; вопросы не повторяют уже раскрытое систематически; специалист узнаёт свою практику. Если живой пилот не проведён, техническую демонстрацию можно показать, но качество интервью остаётся непроверенной гипотезой.

### 8.1. Качество входа и надёжность вклада

Анкета сообщает роль, опыт, обязанности и условия со слов участника. Экстрактор использует её для понимания контекста, интервьюер — для уточнений по зоне ответственности. Факты карточки опираются на реплики интервью. Отступление от заявленной роли само по себе не делает случай нерелевантным.

После отправки ответа система автоматически определяет, относится ли он к рабочему случаю, требует пояснения, не связан с ним или содержит отказ. Оценка сохраняется рядом с результатом извлечения. Интервьюер получает до трёх ранее принятых реплик с вопросами в пределах текущего случая. Посторонние ответы и реплики из других случаев исключаются из этого контекста.

Расширенная анкета со стеком, типом системы и зоной ответственности — следующий слой. Новые поля передаём отдельно от ответов. Историю из других интервью и прежние карточки в MVP автоматически не загружаем. После настройки прав они могут служить подсказкой для вопроса. Переносить утверждение в новый случай можно после подтверждения участником.

| Ситуация | Поведение и критерий проверки |
|---|---|
| Общие обязанности или слишком общий ответ | Попросить один эпизод. Из списка обязанностей не создавать тему или карточку случая |
| Бессвязный ответ, шутка, реклама или попытка перевести модель на другую задачу | Сохранить реплику в истории. Если её связь с рабочим случаем не понятна, предложить пояснить или сменить эпизод. Пробелы по такой реплике не закрываются, новые факты в карточку не попадают |
| Короткий ответ с понятной связью | Принять содержательную деталь. Например, после вопроса о действии «добавил индекс» фиксирует действие, а эффект остаётся неизвестным |
| Участник описывает работу команды или чужой опыт | Спросить, что он сделал или наблюдал лично. Сохранить командный, чужой или неопределённый вклад без повышения уверенности в авторстве |
| Противоречие или сомнительное причинное объяснение | Спросить об основании или проверке. Если уточнение не устраняет сомнение, сохранить его как пробел и передать на редакторскую проверку |
| Серия неполных или посторонних ответов | Предложить другой случай. Сессия продолжается до команды участника завершить интервью |
| Недостаточно материала для публикации | Сохранить приватный черновик. На этапе публикации редактор может вернуть его с причиной, например «неясно личное участие» или «не описана проверка результата» |

**Важность информации для интервью** определяется пользой для разбора случая. Приоритет у того, что меняет понимание задачи, выбор решения, границы применимости или оценку результата. Частоту и последствия ошибки учитываем, если участник их назвал. Оценка вклада ведётся по конкретности, понятности личного участия, наличию оснований и способу проверки. Значимость задачи и надёжность утверждений фиксируются отдельно.

**Подтверждение квалификации** относится к приглашению и редакторской проверке. Должность, стаж из анкеты и уверенный тон сами по себе ничего не подтверждают. Интервьюер отмечает проверяемые признаки материала: относится ли реплика к случаю, кто действовал, какие есть подтверждения и что остаётся неясным. Выводы о состоянии человека и общий рейтинг эксперта из ответов не формируются.

На этапе 6 проверяем, что слабая карточка остаётся приватной и редактор может назвать причину возврата. На этапе 7 прогоняем строки таблицы на синтетических и живых примерах, в том числе ложное отклонение короткого уместного ответа и повтор посторонних реплик. Проверку происхождения и независимых подтверждений расширяем после MVP по Dataflow.

## 9. Как распределить работу

| Участок | Ответственность | Первая точка интеграции |
|---|---|---|
| Сценарии и качество | Темы, источники, разбор интервью, оценка вопросов и карточек | Проверочные случаи и замечания первого специалиста |
| Ядро интервью | Экстрактор, состояние, правила, интервьюер, сохранность | Один работающий ход с сохранением ответа |
| Web и публикация | Вход, интерфейс разговора, черновик, редактор, каталог | Экран на реальном ходе backend |
| Синтез и данные | Схема карточки, связи с ответами, синтез, происхождение | Карточка из сохранённого интервью |

Это участки ответственности, не требование четырёх разработчиков или отдельных сервисов. При небольшой команде участки объединяются. Синтез подключается к реальному транскрипту рано; frontend не ждёт завершения всех модулей. Общее состояние и формат ответа сначала согласуют владельцы ядра и синтеза, затем фиксируют в коде.

## 10. Что делаем следующим

1. Проверяем пригодность минимальной кодовой основы и доступ к LLM.
2. Выбираем первую тему и готовим 6 проверочных сценариев с ожидаемым поведением.
3. Реализуем один цикл интервью и синтез черновика без полного интерфейса.
4. Проверяем его со специалистом и исправляем содержательные ошибки.
5. Только после этого доводим web, проверку и каталог до сквозного показа.

Если времени не хватает, сокращаем число тем и оформление каталога. Сохранность ответов, контроль доступа, происхождение материала и проверку отсутствия выдуманных фактов не снимаем. Голос, Telegram и автоматизация импорта не вытесняют работу над качеством интервью.
