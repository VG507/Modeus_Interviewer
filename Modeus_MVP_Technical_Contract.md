# Modeus MVP: общий технический контракт

Версия 1.0 · 17 ноября 2026 года. Договор для реализации, не описание готового приложения.

## 1. Область действия

Продуктовые требования определяет [основной MVP-план](Modeus_Interview_MVP_Plan.md); этот файл закрепляет технические стыки четырёх ролей. Ролевые планы определяют порядок задач. Dataflow используется после готового MVP. Telegram и STT сейчас не реализуются.

Первый проверенный сценарий относится к Python backend. MVP охватывает стартовые профили Python backend, frontend, QA и DevOps. В открытом интервью участник указывает роль, а тема определяется по рассказу. Планировщик разбирает один случай за раз, затем предлагает следующий. Участник сам завершает интервью. Результат: адаптивное текстовое интервью → приватная карточка → исправление владельцем → согласие → редактор → публичный web-каталог.

API и статусы интервью и карточек ниже задают целевое поведение. Аудит проекта про компетенции и решения по рабочей основе зафиксированы в разделе 3.

Роль 4 добавляет миграции после согласованной текущей вершины; роль 2 проверяет единый порядок. Изменение чужого интерфейса сначала отражается в этом договоре и примерах.

## 4. Общие правила данных

- ID — непрозрачные строки, назначенные сервером; версии — целые числа от 1; время — UTC ISO 8601. Клиент не назначает владельца, статус проверки или права.
- `origin: human | synthetic` задаётся доверенным серверным сценарием создания сессии и наследуется карточкой. Обычный клиент не может менять его. Технические синтетические примеры загружаются подготовленным сценарием команды, без отдельного пользовательского test/live-интерфейса.
- Анкета хранится снимком в сессии: `role`, `experience`, `responsibilities`, `conditions`. Сохраняем свободный текст роли и определяем подходящий `profession_id` по конфигурации профилей и синонимов. При неоднозначном или неизвестном профиле ведём интервью без сводки.
- У записи есть `id`, `created_at`, `updated_at`. Сессия и карточка имеют отдельные `version`. Их версия меняется при каждом применённом изменении, включая обработку.
- Сообщение хранит `session_id`, `sequence`, `kind: question | answer | control`, `text`, `reply_to_question_id`, `status: draft | queued | processing | processed | failed`, извлечение и технические сведения обработки. `reply_to_question_id` обязателен для ответа. Для управляющего сообщения текст/ссылка могут отсутствовать.
- Существенный факт: `{id, field, text, supporting_message_ids}`. Допустимые `field`: `task`, `context`, `action`, `decision`, `verification`, `error`, `limitation`. Все ссылки ведут на ответы той же сессии. Клиент не получает служебные поля по умолчанию.
- Состояние случая: `facts[]`, `gaps[]`, `asked_intents[]`, `declined_intents[]`, `followups_without_new_information`. Пробел: `{field, status: unknown | ambiguous | not_applicable, note}`. Неизвестное не заменяется догадкой; отказ хранится отдельно.
- Извлечение: `{message_id, schema_version, facts[], gaps[], declined_intents[], new_topic_notes[], assessment}`. Автоматическая оценка ответа: `relevant | unclear | unrelated | declined`. В истории API поле `assessment` равно `null` у старых реплик и до обработки. Неясная или посторонняя реплика сохраняется в истории без фактов для карточки.
- Источник: URL, дата получения и текст; тема хранит `source_ids`. Источники объясняют тему, но не доказывают опыт человека.

### Импорт и обработка вакансий

| Слой | Формат и обработка |
|---|---|
| Импорт | Адаптируем последовательность `compare_competencies`: OAuth, поиск с пагинацией и фильтрами, подробности по ID с ограничением частоты и повторами временных сбоев. Ориентир — 50 уникальных вакансий за 30 дней на профиль. Стартовые ID: `python_backend`, `frontend`, `qa`, `devops`. Регионы, запросы и синонимы задаются конфигурацией. В БД Modeus храним источник, внешний ID, канонический URL, даты публикации и проверки, очищенный текст и нужные поля HH. Повторный импорт сверяет пару «источник + внешний ID», при отсутствии ID — канонический URL. Одна вакансия может подходить нескольким профилям. |
| Извлечение | Объединяем навыки из `key_skills` и очищенного текста с нормализацией и удалением дублей. Локальная LLM извлекает контекст задач, навыки, инструменты, явно указанный уровень и условия по JSON-схеме. Для опыта используем структурированное значение HH, если оно есть. Описания передаются модели как данные. Backend сверяет цитаты и ссылки, а для структурированных полей сохраняет путь к полю источника. Пропущенные значения остаются пустыми. Повторно обрабатываем новые и изменённые вакансии либо вакансии со старой версией схемы извлечения. |
| Сводка | Backend приводит названия к общим терминам, исключает повторные объявления одной компании и считает число уникальных вакансий, подтверждающих каждый пункт, в пределах профиля. Перед обновлением проверяет полноту прогона. Сохраняет время успешного обновления, размер выборки и ссылки на источники. |

Формат структурированной записи для дальнейшего сопоставления с карточками интервью:

```text
{schema_version, profession_id, title, task, skills[], tools[], experience_band, level, conditions, evidence[]}
evidence: {field_path, vacancy_id, url, quote?, source_field?}
```

Одна запись описывает одну рабочую задачу. Для навыков и инструментов храним нормализованные идентификаторы. Происхождение знания фиксируем типом записи и ссылками на источники. Для сопоставления карточка интервью может хранить профиль, задачу и необязательные нормализованные метки навыков и инструментов по каждому случаю. Метки опираются на ответы и не наследуются из вакансий. Рабочие действия, решения и проверки в экспертной карточке опираются на сообщения интервью. Будущая карта обучения связывает рыночные задачи и навыки с экспертными примерами по профилю, задаче и нормализованным навыкам. Предпосылки и последовательность обучения требуют отдельного этапа.

Служебная страница «Вакансии» доступна редактору. Она запускает фоновый сбор по выбранному профилю, показывает состояние и время последнего успешного обновления. Список подготовленных карточек фильтруется по `profession_id`, `experience_band` и `level`. Карточка показывает задачу, навыки, инструменты, доступные требования к опыту и уровню, короткое основание и ссылку на вакансию.

Ручной запуск со страницы, CLI и расписание используют одну операцию. Она собирает и проверяет выборку, затем атомарно обновляет используемые карточки и сводку по каждому профилю. Параллельный повтор одного профиля пропускаем. Расписание — понедельник, 09:00, `Europe/Moscow`. После сбоя предыдущая сводка используется до 14 дней с успешного обновления.

В интервью используем готовые данные БД. Подбор начинает с профиля и сопоставляет требуемый опыт и уровень с указанными в анкете. Стаж и уровень храним отдельно, уровень из количества лет не выводим. При отсутствии данных используем только известные признаки. Из подходящих карточек выбираем небольшое число фрагментов по теме, задачам и стеку текущего случая. Подбор применяется только к уточнениям. Если совпадения нет, вопрос строится по анкете и ответам. Вакансии обрабатывает локальная модель Modeus.

Проверенные источники вносим вручную или через еженедельную очередь кандидатов. Расширяем существующую схему `Source` заголовком, первоисточником, профилями, темами, применимыми версиями, датой публикации и датой редакторской проверки. Для каждой подборки сохраняем ID использованных источников. Генератор получает короткую заметку о применимости и последнюю реплику. Вакансии и литература дают идеи для одного естественного уточнения. Основания для фактов в карточке берём из ответов.

**Обновление банка.** Раз в неделю собираем новые публикации и проверяем изменения выбранной документации и заметок о релизах. Для DEV используем поиск по темам или хронологическую ленту, для daily.dev — поиск или общие ленты с учётом доступных квот. Идентификатор источника, канонический URL и связь с исходной публикацией позволяют удалять дубли и учитывать перепечатки как одно наблюдение. Новый или содержательно изменившийся материал получает статус «на проверке». Редактор связывает его с рабочей задачей и указывает основание. Повторная загрузка сама по себе не обновляет дату содержательной проверки.

Плановый пересмотр наступает через три года после публикации либо последней проверки, если она уже была. Для материала старше пяти лет сохраняем явные границы применимости. Изменения API и статуса поддержки версии запускают перепроверку раньше. Срок в 14 дней относится к оперативной сводке вакансий. Для практического совета отдельно сохраняем период применения экспертом, версию, ограничения среды, ID сообщения и при наличии ссылку на проверенный материал. Если данных недостаточно, редактор видит причину пометки «требует уточнения».

**Профиль проектов.** В `context.projects` можно вручную внести до трёх записей. В каждой записи обязательна задача (`task`), остальные поля необязательны (`period`, `role`, `responsibility`, `stack`, `constraints`). Лимит поля — 300 символов. Старые анкеты и пустой список поддерживаются. Модель получает проекты в контексте анкеты, а факты карточки извлекает из ответов. На следующем этапе локальное извлечение из добровольно загруженного резюме создаёт редактируемый черновик тех же полей. В интервью поступают только подтверждённые поля. Контакты и исходный документ для этого процесса хранить не требуется. Основание вклада отмечаем на уровне темы или утверждения и связываем с ответом эксперта. Оно может отражать рабочий опыт, пилот, оценку технологии или мнение по публикациям.

**История наблюдений.** Для MVP сохраняем дату наблюдения, профиль, технологию, задачу, тип свидетельства и ссылку на источник. У недельной выборки HH фиксируем регион, фильтры, период, число подходящих вакансий, общее число уникальных вакансий и число работодателей. Сводку для интервью можно обновлять, датированные результаты сохраняем для сравнения периодов. Отдельно учитываем независимые описания внедрения и отказа, а также мнение эксперта с основанием. Популярность публикации используется при отборе материалов для чтения.

После MVP регистрируем проверяемую гипотезу до прогнозного периода. Фиксируем исходный показатель, ожидаемое изменение, горизонт и правило проверки. По окончании периода сохраняем измеренный результат и сравнение с сохранением исходной доли на той же выборке по роли и региону. Ошибочные прогнозы остаются в истории. Редактору доступны абсолютные числа и ограничения сравнения.

Проверки расширения MVP включают старую, применимую к своей среде практику, свежую статью об удалённом API, пустой профиль, мнение без личного внедрения и две перепечатки одного анонса. Воспроизводим повтор еженедельного сбора и проверяем, что он не удваивает наблюдения и не продлевает срок редакторской проверки.

Приёмка: сценарии импорта на сохранённых ответах HH, фильтры и доступ к странице, несовпадающая роль и уровень, отсутствие совпадений, обновление без дублей. Для двух профилей сравниваем вход генератора и качество уточнений на одинаковых ответах с источниками и без них. Аналитика вакансий, сравнение с учебными программами и построение карты обучения относятся к следующему этапу.

JSON-поля достаточны для извлечения, состояния и содержимого карточки. Таблицы и отдельная поисковая инфраструктура не создаются по числу логических терминов.

## 5. Статусы и обработка интервью

Сессия: `active | completing | completed`. Отдельно `processing_status: idle | queued | running | failed`, `processing_stage: initial_question | extraction | question | synthesis | null`, `current_question_id`, `card_id`, `version`, `error`.

| Событие | Изменение |
|---|---|
| Создание сессии | `active`, постановка первого вопроса в обработку; после сохранения вопроса — `idle` |
| Сохранение текста | Создаётся `draft` ответа; модель ещё не вызывается |
| Отправка черновика | Ответ фиксируется, становится `queued`; сессия остаётся `active` |
| Успешный ход | Извлечение и состояние сохранены. Интервьюер задаёт уточнение или начинает следующий случай |
| Пропуск | Сервер фиксирует отказ от текущего намерения и выбирает другое уточнение или переходит к следующему случаю |
| Завершение пользователем | `completing`, ответы больше не принимаются. Запускается синтез |
| Ошибка обработки | Статус этапа `failed`, сохранённые данные остаются; доступен повтор этого этапа |
| Сохранение карточки | `completed`, `idle`, задан `card_id` |

Текст сохраняется до вызова модели. Раздельные сохранение и отправка обеспечивают правку до обработки: обновление `draft` допустимо, изменение отправленного ответа — нет. Уточнение после обработки передаётся новым ответом на актуальный вопрос. На вопрос допускается один незавершённый черновик.

При смене случая backend сохраняет его факты и пробелы в `past_cases` и сбрасывает состояние уточнений. Для открытого интервью он просит рассказать другой эпизод и выводит название, когда ответ содержит конкретную задачу. Название хранится в сессии, отдельно от общего каталога. Для целевого интервью backend выбирает следующую подготовленную тему той же профессии. `topic_id` хранит стартовую тему или внутреннее значение `open-interview`, `current_topic_title` показывает текущую. Карточка нескольких случаев группирует их в `content.cases`.

Анкету, факты случая и свежие реплики передаём модели раздельно. Модель получает текущий ответ или его фрагмент и до трёх уместных пар из текущего случая. В каждой предыдущей паре вопрос ограничен 120 символами, ответ — 240. Экстрактор получает до трёх выдержек о задаче, генератор вопроса — до 12 последних фактов. Форма допускает до 8000 символов в новом ответе. История других интервью и карточек из других сессий в этот контекст не загружается.

Проверка локального Ollama 18 ноября показала рабочее окно 4096 токенов по `/api/ps`. Modeus делит длинный ответ для экстракции на части до 3200 символов, по возможности по границе предложения. Формулировка вопроса использует начало и конец длинного ответа и подтверждённые факты, в том числе из середины. Полный текст ответа хранится в истории. При синтезе модель может упорядочить от 2 до 20 фактов одного случая по коротким цитатам. Большие наборы фактов и карточки из нескольких случаев выводятся в порядке сохранения. До выпуска нужен замер входных токенов на реальной модели.

Один активный ход на сессию обеспечивается атомарной операцией БД и устойчивой записью задания. Поставленные задания и их стадия переживают перезапуск процесса. Достаточны запись в БД и обработчик внутри того же приложения; отдельный брокер не обязателен. Зависшая обработка переводится в повторяемую ошибку после ограниченного срока аренды задания, выбранного при настройке таймаутов.

Каждая стадия сохраняет результат до перехода к следующей. Если генерация вопроса упала после успешной экстракции, повтор не извлекает те же факты заново. Запись результата проверяет актуальную версию и токен задания; устаревший результат отклоняется. Сетевой вызов LLM не удерживает транзакцию/блокировку БД.

Команда завершения разрешена и во время вызова модели. Сервер закрывает приём ответов и заменяет активное задание. Если последний отправленный ответ ещё не разобран, задача завершения извлекает из него факты перед сборкой карточки. При сбое доступен повтор завершения. Несданный `draft` остаётся за пределами карточки. Разрешён частичный итог с явными пробелами.

## 6. HTTP API v1

Базовый путь — `/api/v1`; JSON, поля в `snake_case`. При необходимости адаптируем существующие маршруты основы к этому внешнему договору. Все приватные операции используют общую проверку пользователя. Чужой приватный объект возвращает `404`, отсутствие входа — `401`, отсутствие роли для редакторской операции — `403`.

| Метод и путь | Вход / результат | Ведущий |
|---|---|---|
| `POST /auth/login` | `{email, password}` → `200 {id, is_editor}` и cookie сессии | Основа |
| `POST /auth/logout` | Отозвать сессию и очистить cookie → `204` | Основа |
| `GET /me` | `{id, is_editor}` для действующей сессии, иначе `401` | Основа |
| `GET /topics` | `{items: [{id, profession_id, title}]}` | 2; данные 1 |
| `POST /interviews` | `{context, topic_id?}` → сессия, `201`. Без `topic_id` первый вопрос открытый. При заданном ID используется подготовленная тема | 2 |
| `GET /interviews` | Список собственных сессий | 2 |
| `GET /interviews/{id}` | Сессия, публичное для владельца состояние обработки, сообщения и текущий вопрос | 2 |
| `POST /interviews/{id}/answers` | `{expected_version, question_id, text}` → сохранённый `draft` и новая версия, `201` | 2 |
| `PATCH /interviews/{id}/answers/{answer_id}` | `{expected_version, text}` → изменённый `draft` и версия | 2 |
| `POST /interviews/{id}/answers/{answer_id}/submit` | `{expected_version}` → состояние принятой обработки, `202` | 2 |
| `POST /interviews/{id}/skip` | `{expected_version}` → состояние принятой обработки, `202`; допускается только при `active/idle` | 2 |
| `POST /interviews/{id}/finish` | `{expected_version}` → `completing`, `202` | 2 |
| `POST /interviews/{id}/retry` | `{expected_version}` → повтор текущего неудачного этапа, `202` | 2; синтез 4 |
| `GET /cards` | Собственные карточки; редактор получает очередь через `?scope=review` и публикации через `?scope=published` | 4 |
| `GET /cards/{id}` | Приватная карточка владельцу или редактору переданного материала | 4 |
| `PATCH /cards/{id}` | `{expected_version, content, text}` или `{expected_version, title?, text}` → новая версия черновика | 4 |
| `POST /cards/{id}/submit-review` | `{expected_version, consent: true, show_author: boolean, author_name?}` → карточка на проверке | 4 |
| `POST /cards/{id}/review` | `{expected_version, decision: accept | return | keep_private, comment}` → карточка; для `return` причина обязательна | 4 |
| `POST /cards/{id}/unpublish` | `{expected_version, comment}` → приватный черновик; только редактор, причина обязательна | 4 |
| `GET /catalog` | `{items, next_cursor}`; только опубликованное | 4 |
| `GET /catalog/{id}` | Публичное представление или `404` | 4 |

Пагинация интервью, карточек и каталога использует `limit` (по умолчанию 20, максимум 100) и необязательный `cursor`. Ответ содержит `{items, next_cursor}`. Темы возвращаются одним списком. Каталог доступен без входа. Клиент опрашивает состояние во время обработки. Для изменяющих запросов из браузера сервер проверяет точное совпадение `Origin` с `APP_ORIGIN`.

Для изменяющих запросов к интервью и карточкам обязателен `Idempotency-Key`. Клиент создаёт ключ для нового действия и сохраняет его при сетевом повторе. Область уникальности включает пользователя, метод, путь и ключ. Повтор с тем же телом возвращает ранее принятый результат без повторного эффекта, даже если `expected_version` устарела. Тот же ключ с другим телом даёт `409 IDEMPOTENCY_CONFLICT`. Записи принятых действий хранятся на срок жизни объекта MVP. Сервер проверяет актуальные права и при повторе. Вход и выход используют отдельный контракт cookie-сессии.

Схемы и JSON-примеры для первого диалога закреплены в [материалах шага 2](docs/Step_2_Interview.md). Переход от черновика к сохранённому следующему вопросу проверяем на шаге 3. Форматы карточек и редакторских операций закрепляем перед подключением их экранов.

Новая команда с неверной версией — `409 VERSION_CONFLICT`. Клиент перечитывает объект; не повторяет изменяющий запрос автоматически с новой версией. Конкурирующий ход — `409 PROCESSING_IN_PROGRESS`; исключение — завершение по правилам раздела 5. Лимиты размера текста задаёт сервер и публикует в API-схеме до подключения frontend.

Единая ошибка:

```json
{"error":{"code":"VERSION_CONFLICT","message":"Состояние изменилось. Обновите данные.","retryable":false,"request_id":"req_01","current_version":8}}
```

`400/422` — неверные данные (`VALIDATION_ERROR`), `409` — конфликт или недопустимый переход (`INVALID_STATE`), `429` — ограничение частоты, `500` — внутренняя ошибка без деталей секретов. Для фонового сбоя HTTP чтения остаётся `200`, а объект содержит `error` с `code: LLM_UNAVAILABLE | INVALID_MODEL_OUTPUT | PROCESSING_TIMEOUT`, безопасным текстом и `retryable: true`. Провайдерские ключи и сырой ответ провайдера клиенту не возвращаются.

## 7. Стык роли 2 → роль 4: синтез

Внутренний вызов `synthesize(snapshot)`, не отдельный публичный сервис. Вход фиксируется при завершении:

```json
{
  "schema_version": 1,
  "session_id": "session_01",
  "completion_version": 8,
  "owner_id": "user_01",
  "origin": "human",
  "topic_id": "topic_sql",
  "context": {"role":"Python backend","experience":"3 года","responsibilities":"API и БД","conditions":"PostgreSQL"},
  "messages": [],
  "case_state": {"facts":[],"gaps":[],"asked_intents":[],"declined_intents":[],"followups_without_new_information":0},
  "extractions": []
}
```

В `messages` входят сохранённые вопросы, отправленные ответы и управляющие события в порядке `sequence`; схема сообщения — раздел 4. Массивы примера пусты только для краткости. Наличие экстракции не обязательно для каждого ответа. Снимок неизменяем, его ID/версия используется для повтора.

Выход синтезатора: `{schema_version, session_id, completion_version, content, text}`. `content` содержит `title` и массивы фактов по полям `task`, `context`, `actions`, `decisions`, `verification`, `errors`, `limitations`, а также `unknown_fields[]`. Каждый факт хранит `id`, `text`, `supporting_message_ids`; неизвестные разделы могут быть пустыми. `text` — читаемое представление этого содержания, без добавления новых утверждений.

Проверка схемы и ссылок выполняется до сохранения. Семантическая оценка роли 1 обязательна отдельно. Только сервер добавляет владельца, происхождение и статусы. На `session_id` действует уникальность карточки MVP: повтор синтеза не создаёт вторую. Роль 4 сохраняет карточку, затем роль 2 связывает её с сессией и фиксирует `completed`; в одном backend это одна транзакция. Если синтез упал, сессия остаётся `completing/failed`, повтор использует тот же снимок. При сбое после сохранения поиск по `session_id` возвращает существующую карточку.

## 8. Правки и публикация

Карточка содержит `id`, `session_id`, `owner_id`, `version`, `origin`, `content`, `text`, исходный результат синтеза и журнал правок. Добавленный владельцем факт имеет `source: owner_edit`, пустые `supporting_message_ids` и связь с записью правки; исходный факт — `source: interview`. Сервер сохраняет происхождение изменённых фактов по сравнению с прежним содержимым, не доверяя клиентской метке. Изменённый `text` также сохраняется как явная правка владельца и проверяется редактором целиком. Новые утверждения не приписываются исходному диалогу.

Веб-форма редактирует название и текст. При изменении текста без поля `content` старая структура сохраняется в приватной истории, чтобы удалённые утверждения не попали в каталог. Отображаемое имя — выбранное владельцем имя или псевдоним. Если API-клиент включает авторство без имени, применяется подпись «Участник Modeus».

Помимо общей `version` карточка хранит `content_version`: она начинается с 1 и увеличивается только при правке содержания или отображаемого авторства. Изменение статусов увеличивает общую `version`, но не `content_version`. Согласие и решение редактора относятся к конкретной `content_version` (хранятся версия, пользователь, время). Публикационный статус отделён от проверки:

| Действие | publication_status | review_status | Дополнительное правило |
|---|---|---|---|
| Синтез | `draft` | `unreviewed` | Согласия нет |
| Передача с согласием | `in_review` | `unreviewed` | Согласие записано для текущего содержания |
| Принятие редактором | `published` | `reviewed` | Проверены согласие и версия |
| Возврат | `draft` | `needs_changes` | Причина сохранена |
| Оставить приватно | `draft` | `unreviewed` | Согласие на отправку сброшено, комментарий сохранён |
| Правка владельцем | `draft` | `unreviewed` | Прежнее согласие/одобрение больше не действует; нужна новая отправка |
| Снять с публикации | `draft` | `needs_changes` | Причина сохранена; каталог сразу закрывает карточку |

Правка `published` через PATCH возвращает `409 INVALID_STATE`. Редактор снимает карточку с публикации, владелец правит черновик и заново отправляет его с согласием на публикацию текущей версии. После принятия редактором карточка снова появляется в каталоге. Новые вклады и версии опубликованных материалов вне MVP. Редактор получает доступ к материалу после передачи на проверку и сохраняет служебный доступ для повторной проверки/снятия; произвольные чужие непереданные черновики ему не открываются.

Публичная схема разрешает только `id`, `title`, `profession_id`, название темы, `content` без внутренних ID/ссылок на сообщения и истории правок, `text`, `reviewed_at` и выбранное владельцем отображаемое авторство. `owner_id`, контекст анкеты, диалог, исходная экстракция, ошибки обработки и журнал проверок исключены. Публичное содержание также проверяется редактором на персональные/закрытые сведения; исключение служебных полей само по себе не обезличивает текст.

## 9. Запуск, конфигурация и работа в Git

После аудита роль 2 закрепляет реальные пути и команды в корневом README: установка → `.env.example` → миграции → начальные темы/пользователь редактора → backend → frontend → проверки. Команды воспроизводимы на чистом checkout; демонстрационные данные не копируют чужие пользовательские БД. Версии зависимостей фиксируются lock-файлами выбранного стека.

В `.env.example` — только имена настроек и безопасные примеры: БД, серверная сессия, LLM-провайдер/модель, ключ, таймаут. Фактические имена выбираются под стек и едины для ролей 2/4. Секреты остаются на сервере и не попадают в frontend, Git и логи. При cookie-входе сервер применяет защиту от CSRF и безопасные параметры cookie; при ином входе роль 2 документирует эквивалентную защиту. Тип входа не выбирается frontend самостоятельно.

Каждая задача идёт в отдельной ветке с коротким PR; перед началом — свежий `main`. В PR: что изменено, затронутые API/миграции и проверка результата. Ведущий участка проверяет стыки. Коммиты и push агента — только после явного разрешения владельца. Текущий контракт сам по себе разрешения не даёт.

## 10. Условия первой интеграции и выпуска

До расширения интерфейса: заполнен раздел 3, в коде есть схемы API с примерами, роли 2/4 провели один ход и синтез, роль 3 подключила реальный запрос, роль 1 разобрала шесть сценариев. Ранний пилот проводится до полного оформления web.

Обязательные автоматические проверки: правила планировщика; права на одиночные объекты и списки; повтор запроса; гонка версий; сбой/повтор каждой стадии; устаревший результат после завершения; восстановление после перезапуска; единственная карточка; публикация только при согласии и решении для актуального содержания; очистка публичного представления от приватных полей.

На совместном прогоне проверяем интервью и публикацию. Пользователь заполняет анкету, отвечает на открытый вопрос, получает уточнение по своему рабочему случаю, обновляет страницу, завершает интервью и правит приватный черновик. Для публикации проверяем отправку с согласием, возврат редактором, повторную отправку, принятие и появление в каталоге. Для исправления опубликованной карточки проверяем снятие из каталога, правку владельцем и повторное согласие и принятие для новой версии. Отдельно проверяем частичный итог и недоступную LLM. Содержание оценивается по основному плану, без дословного эталона ответа модели.

Для показа на хакатоне готовим фрагмент интервью и заранее опубликованную карточку. Показываем, какая деталь рассказа привела к уточнению и какое сведение из ответа появилось в карточке. Указываем происхождение примера.

Ориентир качества — три коротких интервью, включая ранний пилот; авторы просматривают карточки, другую экспертную проверку проходит хотя бы одна. При отсутствии живого пилота выпуск является технической демонстрацией с непроверенным качеством интервью.

Основа следующего этапа уже здесь: внутренние ID, серверные права, общий цикл подтверждённого текста, происхождение, ссылки на сообщения и версии. Дополнительные каналы, STT, аудио и расширенные сущности Dataflow добавляются после готового MVP.
