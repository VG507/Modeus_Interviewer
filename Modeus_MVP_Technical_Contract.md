# Modeus MVP: общий технический контракт

Версия 1.0 · 17 ноября 2026 года. Договор для реализации, не описание готового приложения.

## 1. Область действия

Продуктовые требования определяет [основной MVP-план](Modeus_Interview_MVP_Plan.md); этот файл закрепляет технические стыки четырёх ролей. Ролевые планы определяют порядок задач. Dataflow используется после готового MVP. Telegram и STT сейчас не реализуются.

Одна профессия, первая тема — диагностика медленного SQL-запроса. Один рабочий случай на сессию. Результат: адаптивное текстовое интервью → приватная карточка → исправление владельцем → согласие → редактор → публичный web-каталог.

Зафиксированные ниже API и статусы — целевой договор новой реализации. Технологии исходного проекта ещё не проверены. Аудит может изменить привязку к стеку, но не должен молча менять договор между ролями.

## 3. Технологическая фиксация на этапе 0

Архитектура: один backend, один web-клиент, одна реляционная БД. LLM вызывается только сервером. Вход, операции интервью и публикация используют один внутренний User ID. Каталог читает безопасное публичное представление карточки.

## 4. Общие правила данных

- ID — непрозрачные строки, назначенные сервером; версии — целые числа от 1; время — UTC ISO 8601. Клиент не назначает владельца, статус проверки или права.
- `origin: human | synthetic` задаётся доверенным серверным сценарием создания сессии и наследуется карточкой. Обычный клиент не может менять его. Технические синтетические примеры загружаются подготовленным сценарием команды, без отдельного пользовательского test/live-интерфейса.
- Анкета хранится снимком в сессии: `role`, `experience`, `responsibilities`, `conditions`. Профессия обозначена `profession_id`; первая — `python_backend`, но структура универсальна.
- У записи есть `id`, `created_at`, `updated_at`. Сессия и карточка имеют отдельные `version`. Их версия меняется при каждом применённом изменении, включая обработку.
- Сообщение хранит `session_id`, `sequence`, `kind: question | answer | control`, `text`, `reply_to_question_id`, `status: draft | queued | processing | processed | failed`, извлечение и технические сведения обработки. `reply_to_question_id` обязателен для ответа. Для управляющего сообщения текст/ссылка могут отсутствовать.
- Существенный факт: `{id, field, text, supporting_message_ids}`. Допустимые `field`: `task`, `context`, `action`, `decision`, `verification`, `error`, `limitation`. Все ссылки ведут на ответы той же сессии. Клиент не получает служебные поля по умолчанию.
- Состояние случая: `facts[]`, `gaps[]`, `asked_intents[]`, `declined_intents[]`, `followups_without_new_information`. Пробел: `{field, status: unknown | ambiguous | not_applicable, note}`. Неизвестное не заменяется догадкой; отказ хранится отдельно.
- Извлечение: `{message_id, schema_version, facts[], gaps[], declined_intents[], new_topic_notes[]}`. Это результат LLM, проверяемый сервером; модель не управляет идентичностью и доступом.
- Источник: URL, дата получения и текст; тема хранит `source_ids`. Источники объясняют тему, но не доказывают опыт человека.

JSON-поля достаточны для извлечения, состояния и содержимого карточки. Таблицы и отдельная поисковая инфраструктура не создаются по числу логических терминов.

## 5. Статусы и обработка интервью

Сессия: `active | completing | completed`. Отдельно `processing_status: idle | queued | running | failed`, `processing_stage: initial_question | extraction | question | synthesis | null`, `current_question_id`, `card_id`, `version`, `error`.

| Событие | Изменение |
|---|---|
| Создание сессии | `active`, постановка первого вопроса в обработку; после сохранения вопроса — `idle` |
| Сохранение текста | Создаётся `draft` ответа; модель ещё не вызывается |
| Отправка черновика | Ответ фиксируется, становится `queued`; сессия остаётся `active` |
| Успешный ход | Извлечение и состояние сохранены; новый вопрос сохранён или начато завершение |
| Пропуск | Сервер фиксирует отказ от текущего намерения и выбирает другое допустимое направление либо предлагает итог; не требует выдуманного текстового ответа |
| Завершение пользователем или планировщиком | `completing`, ответы больше не принимаются; запускается синтез |
| Ошибка обработки | Статус этапа `failed`, сохранённые данные остаются; доступен повтор этого этапа |
| Сохранение карточки | `completed`, `idle`, задан `card_id` |

Текст сохраняется до вызова модели. Раздельные сохранение и отправка обеспечивают правку до обработки: обновление `draft` допустимо, изменение отправленного ответа — нет. Уточнение после обработки передаётся новым ответом на актуальный вопрос. На вопрос допускается один незавершённый черновик.

Один активный ход на сессию обеспечивается атомарной операцией БД и устойчивой записью задания. Поставленные задания и их стадия переживают перезапуск процесса. Достаточны запись в БД и обработчик внутри того же приложения; отдельный брокер не обязателен. Зависшая обработка переводится в повторяемую ошибку после ограниченного срока аренды задания, выбранного при настройке таймаутов.

Каждая стадия сохраняет результат до перехода к следующей. Если генерация вопроса упала после успешной экстракции, повтор не извлекает те же факты заново. Запись результата проверяет актуальную версию и токен задания; устаревший результат отклоняется. Сетевой вызов LLM не удерживает транзакцию/блокировку БД.

Команда завершения разрешена и во время LLM-вызова: сервер фиксирует её, инвалидирует активное задание и закрывает приём ответов. Вызов может закончиться, но его устаревший результат не применяется. Синтез использует все отправленные ответы, включая ответ с неудачной/прерванной экстракцией; несданный `draft` в итог не входит. Разрешён частичный итог, включая пустой материал с явными пробелами.

## 6. HTTP API v1

Базовый путь — `/api/v1`; JSON, поля в `snake_case`. При необходимости адаптируем существующие маршруты основы к этому внешнему договору. Все приватные операции используют общую проверку пользователя. Чужой приватный объект возвращает `404`, отсутствие входа — `401`, отсутствие роли для редакторской операции — `403`.

| Метод и путь | Вход / результат | Ведущий |
|---|---|---|
| `GET /me` | `{id, is_editor}`; подробности входа определяет адаптер после аудита | 2 |
| `GET /topics` | `{items: [{id, profession_id, title}]}` | 2; данные 1 |
| `POST /interviews` | `{topic_id, context}` → сессия, `201`; первый вопрос готовится сервером | 2 |
| `GET /interviews` | Список собственных сессий | 2 |
| `GET /interviews/{id}` | Сессия, публичное для владельца состояние обработки, сообщения и текущий вопрос | 2 |
| `POST /interviews/{id}/answers` | `{expected_version, question_id, text}` → сохранённый `draft` и новая версия, `201` | 2 |
| `PATCH /interviews/{id}/answers/{answer_id}` | `{expected_version, text}` → изменённый `draft` и версия | 2 |
| `POST /interviews/{id}/answers/{answer_id}/submit` | `{expected_version}` → состояние принятой обработки, `202` | 2 |
| `POST /interviews/{id}/skip` | `{expected_version}` → состояние принятой обработки, `202`; допускается только при `active/idle` | 2 |
| `POST /interviews/{id}/finish` | `{expected_version}` → `completing`, `202` | 2 |
| `POST /interviews/{id}/retry` | `{expected_version}` → повтор текущего неудачного этапа, `202` | 2; синтез 4 |
| `GET /cards` | Собственные карточки; редактор получает переданную очередь через `?scope=review` | 4 |
| `GET /cards/{id}` | Приватная карточка владельцу или редактору переданного материала | 4 |
| `PATCH /cards/{id}` | `{expected_version, content, text}` → новая версия черновика | 4 |
| `POST /cards/{id}/submit-review` | `{expected_version, consent: true, show_author: boolean}` → карточка на проверке | 4 |
| `POST /cards/{id}/review` | `{expected_version, decision: accept | return | keep_private, comment}` → карточка; для `return` причина обязательна | 4 |
| `POST /cards/{id}/unpublish` | `{expected_version, comment}` → приватный черновик; только редактор, причина обязательна | 4 |
| `GET /catalog` | `{items, next_cursor}`; только опубликованное | 4 |
| `GET /catalog/{id}` | Публичное представление или `404` | 4 |

Списки принимают `limit` (по умолчанию 20, максимум 100) и необязательный `cursor`, возвращают `{items, next_cursor}`. Каталог без входа. Клиент опрашивает состояние только во время обработки; SSE не требуется. Вход/выход и защита браузерных запросов документируются в разделе 3 до подключения реальных участников.

Для любого изменяющего запроса обязателен `Idempotency-Key`, новый для нового действия, тот же для сетевого повтора. Область уникальности: пользователь + метод + путь + ключ. После аутентификации повтор с тем же телом возвращает ранее принятое значение без повторного эффекта, даже если `expected_version` уже устарела. Тот же ключ с другим телом — `409 IDEMPOTENCY_CONFLICT`. Записи принятых действий сохраняются на срок жизни объекта MVP. Завершённые права проверяются и при повторе; запрещённый доступ не получает сохранённый приватный ответ.

Новая команда с неверной версией — `409 VERSION_CONFLICT`. Клиент перечитывает объект; не повторяет изменяющий запрос автоматически с новой версией. Конкурирующий ход — `409 PROCESSING_IN_PROGRESS`; исключение — завершение по правилам раздела 5. Лимиты размера текста задаёт сервер и публикует в API-схеме до подключения frontend.

Единая ошибка:

```json
{"error":{"code":"VERSION_CONFLICT","message":"Состояние изменилось. Обновите данные.","retryable":false,"request_id":"req_01","current_version":8}}
```

`400/422` — неверные данные (`VALIDATION_ERROR`), `409` — конфликт или недопустимый переход (`INVALID_STATE`), `429` — ограничение частоты, `500` — внутренняя ошибка без деталей секретов. Для фонового сбоя HTTP чтения остаётся `200`, а объект содержит `error` с `code: LLM_UNAVAILABLE | INVALID_MODEL_OUTPUT | PROCESSING_TIMEOUT`, безопасным текстом и `retryable: true`. Провайдерские ключи и сырой ответ провайдера клиенту не возвращаются.

## 7. Стык роли 2 → роль 4: синтез

Внутренний вызов `synthesize(snapshot)`, не отдельный публичный сервис. Вход фиксируется при завершении:

```json
{
  "schema_version": 1,
  "session_id": "session_01",
  "completion_version": 8,
  "owner_id": "user_01",
  "origin": "human",
  "topic_id": "topic_sql",
  "context": {"role":"Python backend","experience":"3 года","responsibilities":"API и БД","conditions":"PostgreSQL"},
  "messages": [],
  "case_state": {"facts":[],"gaps":[],"asked_intents":[],"declined_intents":[],"followups_without_new_information":0},
  "extractions": []
}
```

В `messages` входят сохранённые вопросы, отправленные ответы и управляющие события в порядке `sequence`; схема сообщения — раздел 4. Массивы примера пусты только для краткости. Наличие экстракции не обязательно для каждого ответа. Снимок неизменяем, его ID/версия используется для повтора.

Выход синтезатора: `{schema_version, session_id, completion_version, content, text}`. `content` содержит `title` и массивы фактов по полям `task`, `context`, `actions`, `decisions`, `verification`, `errors`, `limitations`, а также `unknown_fields[]`. Каждый факт хранит `id`, `text`, `supporting_message_ids`; неизвестные разделы могут быть пустыми. `text` — читаемое представление этого содержания, без добавления новых утверждений.

Проверка схемы и ссылок выполняется до сохранения. Семантическая оценка роли 1 обязательна отдельно. Только сервер добавляет владельца, происхождение и статусы. На `session_id` действует уникальность карточки MVP: повтор синтеза не создаёт вторую. Роль 4 сохраняет карточку, затем роль 2 связывает её с сессией и фиксирует `completed`; в одном backend это одна транзакция. Если синтез упал, сессия остаётся `completing/failed`, повтор использует тот же снимок. При сбое после сохранения поиск по `session_id` возвращает существующую карточку.

## 8. Правки и публикация

Карточка содержит `id`, `session_id`, `owner_id`, `version`, `origin`, `content`, `text`, исходный результат синтеза и журнал правок. Добавленный владельцем факт имеет `source: owner_edit`, пустые `supporting_message_ids` и связь с записью правки; исходный факт — `source: interview`. Сервер сохраняет происхождение изменённых фактов по сравнению с прежним содержимым, не доверяя клиентской метке. Изменённый `text` также сохраняется как явная правка владельца и проверяется редактором целиком. Новые утверждения не приписываются исходному диалогу.

Помимо общей `version` карточка хранит `content_version`: она начинается с 1 и увеличивается только при правке содержания или отображаемого авторства. Изменение статусов увеличивает общую `version`, но не `content_version`. Согласие и решение редактора относятся к конкретной `content_version` (хранятся версия, пользователь, время). Публикационный статус отделён от проверки:

| Действие | publication_status | review_status | Дополнительное правило |
|---|---|---|---|
| Синтез | `draft` | `unreviewed` | Согласия нет |
| Передача с согласием | `in_review` | `unreviewed` | Согласие записано для текущего содержания |
| Принятие редактором | `published` | `reviewed` | Проверены согласие и версия |
| Возврат | `draft` | `needs_changes` | Причина сохранена |
| Оставить приватно | `draft` | `unreviewed` | Согласие на отправку сброшено, комментарий сохранён |
| Правка владельцем | `draft` | `unreviewed` | Прежнее согласие/одобрение больше не действует; нужна новая отправка |
| Снять с публикации | `draft` | `needs_changes` | Причина сохранена; каталог сразу закрывает карточку |

Правка `published` через PATCH запрещена (`409 INVALID_STATE`); сначала редактор снимает публикацию. Новые вклады и версии опубликованных материалов вне MVP. Редактор получает доступ к материалу после передачи на проверку и сохраняет служебный доступ для повторной проверки/снятия; произвольные чужие непереданные черновики ему не открываются.

Публичная схема разрешает только `id`, `title`, `profession_id`, название темы, `content` без внутренних ID/ссылок на сообщения и истории правок, `text`, `reviewed_at` и выбранное владельцем отображаемое авторство. `owner_id`, контекст анкеты, диалог, исходная экстракция, ошибки обработки и журнал проверок исключены. Публичное содержание также проверяется редактором на персональные/закрытые сведения; исключение служебных полей само по себе не обезличивает текст.

## 9. Запуск, конфигурация и работа в Git

После аудита роль 2 закрепляет реальные пути и команды в корневом README: установка → `.env.example` → миграции → начальные темы/пользователь редактора → backend → frontend → проверки. Команды воспроизводимы на чистом checkout; демонстрационные данные не копируют чужие пользовательские БД. Версии зависимостей фиксируются lock-файлами выбранного стека.

В `.env.example` — только имена настроек и безопасные примеры: БД, серверная сессия, LLM-провайдер/модель, ключ, таймаут. Фактические имена выбираются под стек и едины для ролей 2/4. Секреты остаются на сервере и не попадают в frontend, Git и логи. При cookie-входе сервер применяет защиту от CSRF и безопасные параметры cookie; при ином входе роль 2 документирует эквивалентную защиту. Тип входа не выбирается frontend самостоятельно.

Каждая задача идёт в отдельной ветке с коротким PR; перед началом — свежий `main`. В PR: что изменено, затронутые API/миграции и проверка результата. Ведущий участка проверяет стыки. Коммиты и push агента — только после явного разрешения владельца. Текущий контракт сам по себе разрешения не даёт.

## 10. Условия первой интеграции и выпуска

До расширения интерфейса: заполнен раздел 3, в коде есть схемы API с примерами, роли 2/4 провели один ход и синтез, роль 3 подключила реальный запрос, роль 1 разобрала шесть сценариев. Ранний пилот проводится до полного оформления web.

Обязательные автоматические проверки: правила планировщика; права на одиночные объекты и списки; повтор запроса; гонка версий; сбой/повтор каждой стадии; устаревший результат после завершения; восстановление после перезапуска; единственная карточка; публикация только при согласии и решении для актуального содержания; очистка публичного представления от приватных полей.

Обязательный совместный прогон: новый пользователь → анкета и тема → ответ с полезным уточнением → обновление страницы → завершение → карточка → правка → согласие → возврат редактором → новая отправка → принятие → каталог → снятие с публикации. Отдельно проверить частичный итог и недоступную LLM. Содержание оценивается по основному плану, без дословного эталона LLM-ответа.

Ориентир качества — три коротких интервью, включая ранний пилот; авторы просматривают карточки, другую экспертную проверку проходит хотя бы одна. При отсутствии живого пилота выпуск является технической демонстрацией с непроверенным качеством интервью.

Основа следующего этапа уже здесь: внутренние ID, серверные права, общий цикл подтверждённого текста, происхождение, ссылки на сообщения и версии. Дополнительные каналы, STT, аудио и расширенные сущности Dataflow добавляются после готового MVP.
