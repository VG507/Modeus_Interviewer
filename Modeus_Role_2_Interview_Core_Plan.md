# Роль 2. Ядро интервью

Дата: 17 ноября 2026 года. Основа: согласованный план «MVP с фокусом на качестве интервью» от 16 ноября.

Это план будущей работы, не отчёт о реализации. Объём: одна профессия (Python backend), несколько подготовленных тем, текстовое web-интервью об одном рабочем случае, черновик, ручная проверка и публичный каталог для хакатона. Главная проверка — содержательное уточнение и полезная карточка без домыслов. Голос, Telegram, мультипрофили, автоматическое объединение, виртуальный эксперт и учебные планы отложены.

Репозиторий проекта: https://github.com/VG507/Modeus_Interviewer . Коммиты на GitHub и push — только после явного разрешения владельца. Эти документы сами по себе такого разрешения не дают.

## Ответственность и результат

Вы отвечаете за экстракцию ответа, состояние сессии, алгоритм выбора цели, LLM-формулировку вопроса и сохранность хода. Результат — запускаемый цикл, который получает ответ, находит полезный пробел и задаёт один уместный вопрос.

Экстрактор закреплён за этой ролью, поскольку он нужен на каждом ходе. Роль 4 согласует формат извлечённых сведений и использует их для синтеза. Не разрабатывать две независимые экстракции.

## Порядок работы

### 1. Проверить минимальную кодовую основу

Кандидат на переиспользование: https://github.com/kr1p043k/compare_competencies . Ранее обсуждался commit 9990d8b2e188722e89ef700889a14b89e25d8955; работоспособность не подтверждена этим планом.

Прочитать инструкции и лицензию, проверить запуск, LLM-клиент, БД и обработку ошибок. С ролью 3 проверить оболочку и вход, с ролью 4 — хранение. Для каждого нужного компонента записать «берём / адаптируем / заменяем / откладываем». Не переносить секреты и чужие данные.

Ориентир первичной проверки — один рабочий блок, до половины дня команды. При блокере оценить конкретный ремонт и минимальную замену. Импорт вакансий и ML-модули не должны блокировать интервью. Проверить доступ к LLM настоящим запросом, модель задавать конфигурацией.

### 2. Согласовать минимальные контракты

С ролью 4 закрепить структуру рабочего случая: задача и условия, действия, решения с основаниями, проверка результата, ограничения и неизвестное. У каждого существенного утверждения — ссылки на сообщения сессии.

С ролью 3 закрепить операции: создать сессию, получить состояние, передать ответ, повторить неудачную обработку, пропустить, завершить и вернуться. Передаются ID сессии, версия состояния и ключ повторной отправки; ответ содержит текущий вопрос, статус обработки или завершения и понятную ошибку. Точные маршруты выбрать после аудита стека, не строить API под предположения.

### 3. Реализовать цикл без полного интерфейса

1. Проверить владельца и сохранить сообщение.
2. Вызвать экстрактор с вопросом, ответом, краткой историей и текущим случаем.
3. Проверить схему, допустимые поля и принадлежность ссылок сессии.
4. Применить результат к ожидаемой версии состояния.
5. Выбрать цель правилом.
6. Вызвать интервьюера с выбранной целью и сохранить вопрос.

Одна модель допустима для всех LLM-задач с отдельными инструкциями. Обычно два вызова на ответ. При завершении вопрос не генерируется. Синтез карточки принадлежит роли 4 и запускается на завершении, не на каждом ходе.

### 4. Реализовать приоритеты планировщика

| Приоритет | Действие |
|---|---|
| 1 | Исполнить команду завершить или пропустить |
| 2 | Уточнить существенную неоднозначность |
| 3 | Получить конкретный случай вместо общего рассказа |
| 4 | Восстановить основные действия |
| 5 | Выяснить основание важного решения |
| 6 | Выяснить проверку результата |
| 7 | Спросить об ошибке или ограничении, если это полезно |
| 8 | Предложить итог |

Пустое поле само по себе не основание для вопроса. Учитывать все аспекты подробного ответа. Отказ прекращает ветку. После двух уточнений без новых сведений предложить другой случай или завершение; не добиваться заполнения всей схемы.

Завершение: понятны задача, существенные условия, основные действия, основание важного выбора и проверка результата. Если значимого выбора нет, фиксируется неприменимость. При команде человека закончить — сохранить частичный результат.

### 5. Подключить web и устойчивость

- Ответ остаётся сохранённым при ошибке LLM или неверной структуре.
- Повторная отправка с тем же ключом не создаёт второй ход.
- У сессии один активный обработчик; устаревший результат не перезаписывает новую версию.
- После перезагрузки возвращается сохранённое состояние, а не новый вопрос.
- Обработка имеет видимый статус и возможность повтора.
- После начала обработки история не редактируется; уточнение передаётся новым сообщением. До обработки разрешена правка последнего ответа.
- Сохраняются модель, версия инструкции и схемы, длительность и ошибка вызова. Не копировать приватные тексты в лишние логи.

Не нужны отдельные микросервисы, универсальный движок workflow или полноценное SSE с воспроизведением событий.

## Проверки

Использовать шесть сценариев роли 1. Автоматически проверить правила и переходы: уже раскрытая проверка не спрашивается повторно, отказ закрывает ветку, завершение не создаёт новый вопрос, повтор сообщения не дублирует ход, устаревший результат отклоняется. На API проверить владельца и сохранность при сбое модели. LLM-вопрос оценивается по смыслу, не точным совпадением строки.

После раннего пилота исправить содержательные ошибки до расширения интерфейса. Если задержка мешает разговору, измерить этапы, затем сократить контекст. Не объединять вызовы ценой потери управляемости без сравнительной проверки.

## Результаты и готовность

- Запускаемый текстовый цикл с инструкцией запуска без секретов.
- Согласованные схемы и примеры запросов/ответов для ролей 3 и 4.
- Пройденные проверки правил, повторов, доступа и ошибок.
- Диалог с человеком содержит полезное уточнение и не повторяет известное систематически.
- Завершение передаёт роли 4 сохранённый транскрипт, структуру случая и происхождение.

Роль 1 отвечает за оценку содержания; роль 3 — за экран; роль 4 — за синтез и хранение карточки. Изменение общей схемы согласуется до реализации. Никакого push без разрешения владельца.
