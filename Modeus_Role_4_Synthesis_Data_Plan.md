# Роль 4. Синтез карточек и данные

Дата: 17 ноября 2026 года. Основа: согласованный план «MVP с фокусом на качестве интервью» от 16 ноября.

Это план будущей работы, не отчёт о реализации. Объём: одна профессия (Python backend), несколько подготовленных тем, текстовое web-интервью об одном рабочем случае, черновик, ручная проверка и публичный каталог для хакатона. Главная проверка — содержательное уточнение и полезная карточка без домыслов. Голос, Telegram, мультипрофили, автоматическое объединение, виртуальный эксперт и учебные планы отложены.

Репозиторий проекта: https://github.com/VG507/Modeus_Interviewer . Коммиты на GitHub и push — только после явного разрешения владельца. Эти документы сами по себе такого разрешения не дают.

## Ответственность и результат

Вы отвечаете за формат и хранение карточки, синтез из нескольких ответов, связи с исходным материалом, происхождение, исправление черновика и серверные правила проверки и публикации.

Экстрактор каждого хода реализует роль 2. Вы совместно определяете формат фактов и пробелов и проверяете его пригодность для синтеза. Не строить второй параллельный разбор того же ответа как обязательный этап.

## Порядок работы

### 1. Согласовать минимальные данные

С ролью 2 проверить существующую БД и утвердить простую схему. Достаточно пользователя, тем и источников, сессии, сообщений и карточки. Извлечение может храниться в сообщении, структура случая — в сессии, содержимое карточки — в JSON-поле. Не каждое логическое понятие требует таблицы.

| Карточка хранит | Назначение |
|---|---|
| ID, владелец, сессия | Идентичность и доступ |
| Название задачи и контекст | Границы применимости |
| Действия, решения и основания | Содержание практики |
| Проверка результата | Как человек понял, что задача решена |
| Ошибки, ограничения, неизвестное | Предохранение от ложного обобщения |
| Ссылки утверждений на сообщения | Проверяемость происхождения смысла |
| human / synthetic | Неизменяемое происхождение материала |
| Публикация и результат проверки | Управление видимостью |
| Согласие, решение редактора, даты | Основание публикации |

Не вводить KnowledgeRelation, независимые подтверждения, версии наборов и поисковый индекс. Если существенный блокер требует изменения схемы, согласовать с ролью 2 до реализации.

### 2. Реализовать синтез на сохранённом диалоге

Вход: транскрипт конкретной сессии, структура случая, результаты извлечения со ссылками и происхождение. Выход: структурированная карточка и читаемый текст. Синтез вызывается по завершении случая, а не после каждой реплики.

Инструкция модели: использовать только рассказанный материал, сохранять отрицания и границы, не делать из ошибки совет, неизвестное оставлять неизвестным. Нельзя добавлять обычные для профессии шаги ради красивой последовательности.

Код проверяет структуру и принадлежность ссылок сессии. Это не доказывает смысловую обоснованность — её проверяет человек с ролью 1. Вакансия обосновывает тему, но не является доказательством действий специалиста.

Первый результат показать на одном реальном транскрипте роли 2 до полного каталога. При сбое синтеза диалог сохранён, доступен повтор. Повтор одного задания не создаёт вторую карточку.

### 3. Реализовать исправление владельцем

Владелец редактирует итоговый черновик, а не всю историю интервью. Сохранять исходный результат синтеза и явные изменения человека в простом журнале или снимке, без универсального сервиса версий.

Добавленные владельцем сведения помечать как его правку, не приписывать их исходным сообщениям. Для синтетической сессии правка не меняет происхождение на human. Если начинается самостоятельный реальный вклад, его оформляют отдельно; сложное смешивание происхождений в MVP не вводим.

Существенные новые утверждения после правки проверяются перед публикацией. Необоснованный совет не становится проверенным только из-за сохранения формы.

### 4. Реализовать серверный поток публикации

Приватный черновик → согласие владельца и передача на проверку → решение редактора → публичный каталог.

Минимальные признаки:

- publication_status: draft / in_review / published;
- review_status: unreviewed / reviewed / needs_changes;
- origin: human / synthetic, независимо от двух статусов выше.

Публикация разрешена при согласии владельца и принятии редактором. Возврат на доработку содержит короткую причину. Редактор может снять проблемную карточку с публикации. После правки материала на проверке старое одобрение не применяется автоматически. Обновление уже опубликованной карточки через новые вклады откладываем.

Публичный API возвращает только опубликованное представление, без приватных сообщений и технических сведений. Приватные операции проверяют владельца или право редактора на сервере. Получение списка черновиков не должно раскрывать чужие записи.

### 5. Согласовать показ и разбор качества

Передать роли 3 примеры полной и частичной карточки, статусы, ошибки и операции черновика/проверки/публикации. Роли 1 — карточку со связями на основания, чтобы разбирать домыслы и потерю смысла.

Синтетические примеры допустимы для технической репетиции и показа, но не являются подтверждением профессиональной достоверности. Их происхождение сохраняется после проверки редактором. При будущей выгрузке или выборке оно должно учитываться явно.

Дубликаты пока разбирает редактор вручную. Сравнение embeddings, LLM-классификацию связей и автоматическое слияние не подключать.

## Проверки

| Случай | Ожидаемый результат |
|---|---|
| В ответах нет причины выбора | В карточке пробел, без догадки модели |
| Рассказан неудачный подход | Обозначен как ошибка или неудача |
| Неполная сессия | Частичная карточка сохраняется приватно |
| Ссылка на чужую сессию | Результат отклоняется |
| Сбой или повтор синтеза | Нет потери диалога и дубля карточки |
| Правка владельца | Новое утверждение различимо от исходного извлечения |
| Нет согласия или решения редактора | Публикация запрещена |
| Посторонний читает черновик | Доступ запрещён |
| Синтетическая карточка принята | origin остаётся synthetic |

Проверки структуры, доступа и переходов автоматизировать на уровне backend. Смысл проверить на сценариях роли 1 и реальном интервью. Не сравнивать синтез с единственным дословным эталоном.

## Результаты и готовность

- Согласованная минимальная схема и миграции после выбора стека.
- Инструкция синтеза, пример входа и полной/частичной карточки.
- Рабочие сохранение, исправление, проверка и публикация.
- Существенные утверждения просмотренных карточек поддержаны ответами или явными правками владельца.
- Автор узнаёт свой опыт; ограничения и неизвестное не исчезли.
- Сквозной путь с ролью 3 доведён до публичной страницы без раскрытия приватного материала.

Ваша роль не включает весь будущий жизненный цикл базы знаний, RAG, граф профессий, автоматические подтверждения, виртуального эксперта или roadmap. Приоритет — один полезный и обоснованный результат интервью.
